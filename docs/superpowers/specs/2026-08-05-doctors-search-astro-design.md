# Поиск врачей на витрине: перевод `/search` на реальный каталог

Дата: 2026-08-05
Статус: согласован, готов к планированию
Область: `healthy-mobile` (Astro-зона `web/`), фронтенд витрины `sdoctorom.health`

## Задача

Страница `/search` рендерит двенадцать мок-врачей из `DOCTOR_MOCKS`, тогда как главная и страницы врачей уже работают на реальном каталоге. На витрине одновременно живут два несовпадающих списка врачей. Нужно перевести поиск на реальные данные, сохранив статическую модель деплоя.

Попутно карточка выдачи опирается на поля, которых в бэкенде нет вообще (рейтинг, расстояние, ближайший слот, признак «принимает новых»), — их приходится убрать, а карточку пересобрать вокруг данных, которые действительно есть.

### Что показал прод

Каталог на момент проектирования — семь верифицированных врачей. Заполненность полей:

| Поле                       | Заполнено | Замечание                          |
| -------------------------- | --------- | ---------------------------------- |
| `specialization`           | 7/7       | свободный текст, разнобой регистра |
| `languages`                | 7/7       | ISO-коды `ru`, `ky`, `en`          |
| `price_from`               | 7/7       | 1000–3000                          |
| `primary_work_city`        | 7/7       | Бишкек ×6, **Ананьево ×1**         |
| `start_practise_date`      | 7/7       | от 1990 года до «три дня назад»    |
| `workplaces`               | 6/7       | у троих по два места               |
| `subspecializations`       | 3/7       |                                    |
| `bio`                      | 2/7       |                                    |
| `avatar_url`               | 1/7       |                                    |
| `consultation_formats`     | 0/7       | пусто у всех                       |
| `rating` / `reviews_count` | 0/7       | `null` и `0` у всех                |

Отсюда три прямых следствия. Фильтр по формату приёма невозможен — он обнулил бы выдачу. Рейтинг убирается не по вкусовым соображениям, а потому что данных нет ни у кого. Врач из Ананьево делает ложным зашитый в страницу заголовок «Найти врача в Бишкеке».

## Решения

### 1. Модель рендеринга: статика, без SSR

`/search` остаётся пререндеренной страницей. Каталог снимается на сборке и инлайнится в HTML, фильтрация выполняется в браузере ванильным скриптом. Модель деплоя не меняется: сайт остаётся набором статических ассетов на Cloudflare без единой Worker-инвокации, а пересборка по durable-флагу `site_rebuild_state` играет роль ISR.

SSR отвергнут: он потребовал бы первого в проекте Worker-скрипта (сейчас `output: 'static'`, в сгенерированном `wrangler.json` нет поля `main`), поставил бы отдачу страницы в зависимость от живого API на каждый просмотр и не дал бы ничего взамен. Индексируемость поиска через SSR не решается — параметрические страницы результатов поисковые системы не индексируют независимо от способа рендеринга.

SEO-поверхность (посадочные страницы вида `/vrachi/{специальность}/` с серверно отрендеренным списком) — отдельная будущая работа, см. «Вне области».

### 2. Общий загрузчик каталога на сборке

Появляется `loadDoctorCatalog(): Promise<DoctorProfileView[]>` — единственная точка получения каталога на сборке, с мемоизацией **Promise** (не результата) на уровне модуля. Все три страницы SEO-зоны переходят на него: `web/pages/index.astro`, `web/pages/search.astro`, `web/pages/doctor/[id].astro`.

Загрузчик выполняет два шага: `searchDoctors()` для получения списка, затем `getDoctorProfile(id)` на каждого врача через пул ограниченной конкурентности.

**Почему это не стоит дополнительных запросов.** Astro вызывает `getStaticPaths` всех динамических маршрутов один раз и строго до рендера страниц; статические маршруты (`/`, `/search`) на этой фазе даже не загружаются. Страница врача уже сегодня загружает полные профили всего каталога. К моменту, когда исполняется frontmatter `/search`, кэш прогрет — стаж и места работы приходят бесплатно.

Более того, сеть разгружается: сейчас `searchDoctors()` вызывается дважды за сборку (из главной и из `getStaticPaths`), после изменения — один раз. Итог за сборку: `ceil(N/100)` запросов каталога плюс `N` запросов профилей.

**Промис кэшируется на всё время жизни модуля и не сбрасывается после разрешения.** Это принципиально: сброс превратил бы кэш в дедуп одновременных вызовов, каталог загрузился бы заново для каждой страницы, и вся экономия исчезла бы. Существующий `src/shared/api/get-me.ts` — **не тот образец**: он намеренно обнуляет промис через `queueMicrotask` в `.finally()`, потому что решает другую задачу. Правильный образец в проекте — `loadYandexMaps` в `src/shared/lib/yandex-map.ts`: промис живёт всё время жизни модуля и обнуляется только при неуспехе. Здесь не нужно и это: по разделу 3 неуспех останавливает сборку, поэтому закэшированный отклонённый промис безвреден, а повторы живут внутри загрузчика.

**Размещение:** `src/entities/doctor/api/load-doctor-catalog.ts`, рядом с `searchDoctors` и `getDoctorProfile`, которые тоже вызываются только на сборке. Слой FSD не нарушается, зависимости — только `shared` и собственный слайс.

Модуль обязан оставаться свободным от побочных эффектов на верхнем уровне (никакого top-level `await`, сетевых вызовов или логирования при импорте) — только объявления и переменная кэша. Это условие того, что он не утечёт в клиентский бандл SPA.

**Оговорка про среду.** Пререндер выполняется не в Node-процессе, а в workerd-изоляте (`@astrojs/cloudflare` поднимает `vite preview` с `prerenderEnvironment: 'workerd'`, а `getStaticPaths` и рендер приходят в него HTTP-запросами). Кэш на уровне модуля там работает — на этом уже держится передача `props` из `getStaticPaths` в рендер. Гарантии, что изолят не будет переработан между запросами, среда не даёт. Цена такого события выше, чем просто повторная загрузка: при холодном кэше маршрутов Astro заново вызывает `getStaticPaths` внутри `getProps`, то есть пострадавший рендер тянет весь каталог целиком. Данные при этом остаются корректными — загрузчик идемпотентен. Если явление проявится, у адаптера есть опция `prerenderEnvironment: 'node'`.

**Влияние на dev-режим:** в `astro dev` каталог замораживается на всю сессию, для свежих данных нужен перезапуск. Это скорее улучшение — сейчас каждое открытие страницы врача заново загружает весь каталог. Поведение документируется в докблоке, гейт по `import.meta.env.DEV` не ставится.

### 3. Устойчивость сборки

Текущая загрузка профилей имеет три дефекта, которые чиним вместе с переездом, потому что общий загрузчик — их естественное место.

**Конкурентность.** `Promise.all` по всему каталогу заменяется пулом на 8–10 параллельных запросов. Готовой утилиты в проекте нет — пишется небольшая функция в `src/shared/lib/`. Сегодня при семи врачах ограничение незаметно, но неограниченный залп — источник исчерпания сокетов и обрыва соединений при росте.

**Асимметрия обработки ошибок.** Сейчас `getDoctorProfile` возвращает `null` при любом неуспешном HTTP-ответе (врач молча исчезает с витрины), но `fetch` не обёрнут в `try/catch`, поэтому транспортная ошибка роняет сборку невнятным исключением. Разводим по смыслу: 404 — врач пропускается, это законная гонка с удалением профиля; 429 и 5xx — повтор, затем остановка сборки; транспортная ошибка — то же, что 5xx.

Текущая сигнатура `Promise<DoctorProfileView | null>` для этого недостаточна: `null` не отличает «нет такого врача» от «сервер отказал». Функция должна возвращать размеченный результат либо бросать на всём, кроме 404.

**Инвариант полноты.** После загрузки сравниваем размер каталога с числом полученных профилей. Расхождение по причинам, отличным от 404, останавливает сборку. У пропусков по 404 тоже есть нижняя граница: если пропущено больше четверти каталога, сборка останавливается независимо от кода ответа — сплошные 404 означают не гонку с удалением, а сменившийся маршрут или неверный `PUBLIC_API_URL`.

Сегодняшнее поведение противоположно и опасно: при исчерпании лимита запросов часть врачей выпадает, сборка завершается успешно и деплоится, а главная продолжает ссылаться на несуществующие страницы. `searchDoctors` уже держит правильную позицию — «лучше не задеплоиться, чем выкатить витрину без врачей», — и `getStaticPaths` ей сейчас противоречит.

**Единый слаг.** Функция `doctorSlug` в `web/lib/slug.ts` уже единственная, и все три страницы зовут её — расхождения реализаций нет. Риск в другом: она принимает `{ id, name }`, а `/search` сегодня передаёт мок-поле `name`, которого в `DoctorProfileView` нет (там `fullName`). При переезде на реальный тип нужно передать правильное поле; ошибка здесь даёт 404 на каждой карточке выдачи и не ловится типами, если объект собирается инлайн. Ссылки строят три страницы, включая главную.

### 4. Контракт поискового индекса

Клиентский скрипт `/search` объявлен как `<script is:inline define:vars={{…}}>`. Такой скрипт Astro **не бандлит и не обрабатывает**: импортировать в него функции из `src/` невозможно. Отсюда главное свойство контракта: **индекс несёт готовые к показу строки**, всё форматирование выполняется на сборке, где хелперы доступны.

```ts
interface SearchIndexItem {
  slug: string
  fullName: string
  initials: string
  avatarColor: string
  avatarUrl: string | null

  specialty: string // подпись для показа, напр. «Стоматолог»
  specialtyKey: string // ключ для фильтра и URL, напр. «стоматолог»
  subspecializations: string[]

  city: string | null
  languages: string[] // подписи для показа: Русский, Кыргызча, English
  languageCodes: string[] // ISO-коды для фильтра и URL: ru, ky, en

  priceLabel: string | null // уже отформатировано: «1 000 с»
  experienceLabel: string | null // уже склонено: «Менее года», «6 лет», «32 года»

  workplaces: { name: string; address: string }[] // не более двух
  workplacesTotal: number // сколько всего, для «ещё N»
}
```

Каждое поле, по которому идёт фильтрация, присутствует в индексе дважды: стабильный ключ для сравнения и подпись для показа. Скрипт не может вывести одно из другого — словари живут в `src/`, а импортировать их ему нечем.

Рядом с индексом в тот же `define:vars` передаются готовые списки опций для двух селектов:

```ts
interface FilterOption {
  key: string // «стоматолог» / «ky» — то, что уходит в URL
  label: string // «Стоматолог» / «Кыргызча» — то, что видит пользователь
  count: number // сколько врачей в каталоге подходит
}
```

Оба списка строятся на сборке из фактического каталога и сортируются по убыванию `count`, при равенстве — по подписи, чтобы порядок опций был детерминирован между сборками.

Тип, функция проекции и построение списков опций живут в `src/entities/doctor/model/search-index.ts` — рядом с `doctor-view.ts`, в том же слайсе и сегменте. Существующая передача `specialtyLabels` из мок-конфига `SPECIALTIES` заменяется этими списками.

`id` не передаётся — он выводится из слага. `bio`, `education`, `appointmentTypes`, координаты мест и `mapImageUrl` в индекс не попадают: они нужны только на странице врача и утроили бы вес. `workplacesTotal` передаётся отдельно, потому что массив обрезан до двух записей и считать «ещё N» по его длине нельзя.

**Бюджет.** Проекция весит около 700 байт на врача в несжатом виде. На текущих семи врачах это порядка 1.2 КБ brotli — примерно 3.6% критического пути страницы. Кириллица в `define:vars` не экранируется в `\uXXXX`, сериализация экранирует только `<`; собственный сериализатор писать нельзя, это открыло бы XSS.

**Порог выноса в отдельный файл — 300 врачей** (эквивалентно блоку данных тяжелее 30 КБ brotli). До него отдельный `/search-index.json` вреден: лишний round-trip на 3G стоит около 300 мс, а экономит доли килобайта.

Проверка бюджета делается интеграцией Astro на хуке `astro:build:done` по образцу `web/integrations/prefetch-list.mjs`, и превышение останавливает сборку. Формулировка «проверять в CI» была бы невыполнимой: конфигурации CI в репозитории нет вообще, есть только `lefthook` на pre-commit, который сборку не запускает.

### 5. Фильтры

Три контрола, все считаются в браузере по инлайновому индексу. Сортировок нет.

**Строка поиска** — по ФИО, специальности и суб-специализациям. По названиям мест приёма поиск сознательно не ведётся; плейсхолдеры, которые сегодня обещают поиск по клинике («Врач, специальность, клиника», «Имя, специальность, клиника»), исправляются на всех четырёх формах — иначе интерфейс обещает то, чего не делает.

**Специальность** — выпадающий список, опции берутся из фактического каталога, а не из статического конфига `SPECIALTIES`: иначе в списке появятся специальности без врачей. Ключ группировки — `trim().toLowerCase()`, подпись — самое частое написание среди врачей этой группы; при равной частоте выбирается вариант, встретившийся первым в порядке каталога, чтобы результат сборки был детерминирован. Маппер уже применяет `normalizeSpecialization` (поднимает первую букву), что схлопывает основной случай разнобоя; группировка по ключу дополнительно покрывает верхний регистр и лишние пробелы.

**Язык приёма** — список из значений, реально встречающихся в каталоге. Коды разворачивает существующий `formatLanguages`: `ru` → «Русский», `ky` → «Кыргызча», `en` → «English».

Фильтр по формату приёма не вводится (`consultation_formats` пуст у всех).

**Контракт URL.** Состояние держится в трёх параметрах: `q` — строка поиска; `specialty` — нормализованный ключ в нижнем регистре (`стоматолог`), не подпись; `lang` — ISO-код (`ky`), не подпись. Ключ и код выбраны как стабильные значения: подписи меняются вместе с данными и оформлением, а ссылки должны переживать это.

Из чтения состояния, из чипов активных фильтров и из их сброса убираются параметры, которых больше нет: `sort`, `rating`, `exp`, `accepting`, `format`, `city`. Сохраняются: работа формы без JavaScript, `history.pushState` и обработка `popstate`.

**Объём выдачи.** Сегодня скрипт рендерит `filtered.slice(0, 30)`, а счётчик показывает полное число совпадений: при каталоге больше тридцати врачей часть выдачи становится недостижимой, а числа в шапке и в списке расходятся. Срез снимается, рендерится вся отфильтрованная выдача. Декоративная пагинация в десктопном шелле (три кнопки без обработчиков) удаляется. Постраничность или виртуализация вернутся вместе с выносом индекса в отдельный файл — на том же пороге в 300 врачей.

**Боковая панель «Все фильтры»** удаляется вместе с обслуживающим её кодом: три контрола помещаются в строку поиска. Удаляются также сортировочные вкладки в мобильном шелле и выпадающий список сортировки в десктопном.

### 6. Карточка врача

Шаблонов два — мобильный (`#card-template`, вёрстка на Tailwind) и десктопный (`#dw-card-template`, вёрстка на классах `dw-*`), у каждого свой рендерер. Оба перекраиваются, состав полей общий, богатство разное.

Показываем: аватар (при отсутствии фото — инициалы на детерминированном цветном фоне), специальность, полное ФИО, суб-специализации, стаж, город, места приёма, цену от и языки приёма. Кнопка ведёт на страницу врача.

Убираем как необеспеченное данными: рейтинг со звёздами и счётчик отзывов, признак «принимает новых», блок «чаще всего обращаются», недельную полосу доступности и «ближайший слот». На десктопе освободившаяся правая колонка карточки отдаётся цене и кнопке записи.

Правила отображения, продиктованные реальными данными:

**Стаж.** `yearsSince` возвращает 0 для врачей, начавших практику в этом году, — таких в каталоге двое. Ноль показывается как «Менее года», остальные значения склоняются по-русски. Склонение уже реализовано во frontmatter `web/pages/doctor/[id].astro`; функция переносится в `src/entities/doctor/lib/doctor-display.ts` к остальным чистым функциям отображения, страница врача начинает звать её оттуда. Третья копия не заводится. Стаж вычисляется на сборке и обновляется при следующей пересборке — для величины, меняющейся раз в год, этого достаточно.

**Город.** Выводится рядом с местом приёма. Без него врач из Ананьево выглядит бишкекским — и это единственное место, где витрина может сказать правду о географии, пока каталог не только бишкекский.

**Места приёма.** Подпись нейтральная — «место приёма», а не «клиника»: среди реальных значений есть «Из дома». Показывается первое место, при `workplacesTotal > 1` добавляется «ещё N». Названия и адреса выводятся через `textContent`, как и сейчас, — среди данных встречается `Клиника "Клиника"`.

Отсутствие любого необязательного поля скрывает соответствующую строку, а не рисует пустую. Врач без мест приёма (такой в каталоге есть) обязан выглядеть корректно.

**Доступность.** Счётчик результатов получает `aria-live="polite"`: выдача целиком перерисовывается скриптом, и пользователь скринридера иначе не узнаёт, что число совпадений изменилось.

### 7. Правки текста и главной

**Числа и география, которые перестанут быть правдой.** На `/search` зашиты «1 200+ проверенных специалистов», « принимают в Бишкеке», заголовок «Найти врача в Бишкеке» (в `<title>`, в H1 и в двух местах клиентского скрипта, включая шаблон «{специальность} в Бишкеке»). На главной — «2 800+ врачей в одном приложении» и кнопка «Найти 2 800+ врачей». Подвал уже сведён к одной строке на весь сайт (см. комментарий в `SiteFooter.astro`) — расхождение цифр там уже чинили.

Все счётчики врачей заменяются числом из фактического каталога. Из заголовков убирается «в Бишкеке»: каталог не только бишкекский, а обещать город, которого может не быть у врача, — та же ошибка, что и обещать 1 200 специалистов при семи.

**Формы главной.** Мобильная и десктопная формы отправляют параметры, которых фильтр не поддерживает: `district`, `clinic`, `format` (три радио «Все / Онлайн / В клинике»), а десктопная — ещё и скрытый `city=Бишкек`. Удаляются сами контролы вместе с их разметкой и стилями, а не только параметры: контрол, который ни на что не влияет, хуже отсутствующего. Мобильная форма не имеет выбора специальности — так и остаётся, специальность на мобильной главной выбирается плитками. Контрол языка на главную не добавляется, он существует только на `/search`.

**Плитки специальностей и разметка на главной.** Восемь плиток, десктопный `<select name="specialty">` и поле `medicalSpecialty` в JSON-LD построены из статического `SPECIALTIES`. Каждая плитка ведёт на `/search?specialty=…` со значением из мок-конфига — после перевода фильтра на реальный каталог такие ссылки будут давать пустую выдачу, а разметка для поисковых систем — перечислять специальности, которых на витрине нет. Всё перечисленное переводится на фактический каталог. Это расширение объёма работ относительно исходной постановки, но без него главная и поиск снова разъезжаются — ровно та проблема, которую эта работа закрывает.

## Проверка

Автотестов в проекте нет (`package.json` не содержит тестового раннера), поэтому проверка ручная и через типы. Чистые функции — проекция индекса, группировка специальностей, склонение стажа — пишутся без побочных эффектов, чтобы их можно было покрыть тестами, когда раннер появится: это уже заявлено в докблоке `doctor-display.ts`.

Изменение считается выполненным, когда:

1. `pnpm typecheck` (`astro check && tsc -b --noEmit`), `pnpm lint` (`oxlint --type-aware`), `pnpm fmt:check` и `pnpm fsd` (`steiger ./src`) проходят без ошибок.
2. Полная сборка проходит на живом API. В `dist/client/search/index.html` присутствуют реальные фамилии врачей из каталога. Строк из `DOCTOR_MOCKS` нет ни в `dist/client/index.html`, ни в `dist/client/search/index.html`, ни в `dist/client/doctor/`. Дополнительно поиск по `web/` не находит ни одного упоминания `DOCTOR_MOCKS` или `doctors.mock`.
   Оговорка: в `dist/client/_astro/*.js` мок-строки останутся, и это ожидаемо — `DOCTOR_MOCKS` попадает в клиентский бандл по независимой цепочке через `doctor.queries.ts` и экраны SPA, которых работа не касается. Критерий «нет нигде в `dist/`» был бы невыполним.
3. Каждая ссылка с карточки выдачи ведёт на существующий файл в `dist/client/doctor/`; число сгенерированных страниц врачей совпадает с размером каталога.
4. Ручная проверка выдачи: пустой запрос показывает весь каталог целиком; фильтр по специальности «Стоматолог» находит всех четверых, несмотря на разное написание в базе; фильтр по языку «Кыргызча» находит троих; несовпадающий запрос показывает пустое состояние, а не ошибку; переход по плитке специальности с главной даёт непустую выдачу.
5. Состояние переживает перезагрузку и кнопку «назад»: ссылка вида `/search?specialty=стоматолог&lang=ky` открывается с уже применёнными фильтрами.
6. Врач без мест приёма, врач со стажем менее года и врач из Ананьево отображаются корректно — без пустых строк, без «0 лет» и без приписывания Бишкека.
7. Сборка останавливается, если API недоступен, если каталог пуст и если профили не загрузились более чем у четверти врачей.

Отдельно фиксируется известное ограничение, не являющееся регрессом: **без JavaScript список врачей не отображается**. Разметка результатов пуста, карточки целиком рисует клиентский скрипт. Формы при этом работают — отправка перезагружает страницу с параметрами в адресе. Так устроена страница и сегодня; серверный рендер карточек решается вместе с посадочными страницами, см. «Вне области».

## Вне области

Следующее сознательно не входит в работу и вынесено с явными порогами.

**Расширение поиска на бэкенде.** Сборка делает `N` запросов профилей подряд, а глобальный ограничитель на бэкенде — 100 запросов в минуту на пару «обработчик и адрес». При каталоге около 60 врачей сборка начинает занимать больше половины этого бюджета, а вторую половину делит с живыми посетителями: страница врача бьёт в тот же обработчик из браузера. Это и есть порог, за которым нужно добавить в выдачу поиска три недостающих поля (`start_practise_date`, `education`, `workplaces`) и убрать запрос-на-врача: тогда 2000 врачей потребуют 20 запросов вместо 2000. Отдельный пакетный или экспортный эндпоинт не нужен — витрине нужны «все», а не произвольные наборы.

**Вынос индекса в отдельный файл и возврат постраничности** — при 300 врачах, см. разделы 4 и 5.

**Перевод SPA на реальный каталог.** Экраны `src/pages/{home,visits,visit-detail,profile}` получают врачей через `DOCTOR_QUERIES` → `getDoctors` / `getDoctorById`, которые до сих пор возвращают `DOCTOR_MOCKS`. Пока это так, мок-данные остаются в клиентском бандле. После перевода `DOCTOR_MOCKS` и `src/entities/doctor/mock/doctors.mock.ts` удаляются целиком, и критерий приёмки можно ужесточить до «нет нигде в `dist/`».

**Фильтр «есть свободная запись» и сортировка по ближайшему слоту.** Самая ценная механика в отрасли: это сортировка по умолчанию у НаПоправку и основа ранжирования Zocdoc, и она же прямо отвечает продуктовой цели «записаться быстрее, чем по телефону». Требует агрегата ближайшего слота в выдаче поиска — отдельная работа с бэкендом.

**Посадочные страницы `/vrachi/{специальность}/`** — единственный способ получать поисковый трафик по запросам вида «стоматолог Бишкек». Там же уместен серверный рендер карточек, который заодно снимает ограничение «без JavaScript список пуст». Делаются к моменту снятия `noindex` (сейчас витрина закрыта от индексации парой: `robots.txt` и мета-тег в обоих макетах).

**Индекс `work_place(doctor_id)` и настройка доверия прокси для ограничителя запросов** — задачи бэкенда, заведены отдельно.
